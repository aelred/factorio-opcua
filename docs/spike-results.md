# Milestone 1 spike results

Measured on 2026-10-16 against Factorio **2.0.77** headless
(`factoriotools/factorio:2.0.77`, base game only) in Docker on the same host
as the client, using `bridge/factorio_opc/rcon.py`. Reproduce with:

```sh
scripts/dev-server.sh up                    # auto_pause=true (default dev settings)
.venv/bin/python spike/spike.py             # add --error-test to include the Lua-error check
```

Absolute timings come from one cloud container and will vary on other
machines; the tick-related behaviour shouldn't.

## Findings

### 1. Commands run once per tick, so a round-trip is one tick (~16.7 ms)
| Measurement (auto_pause off, 300 samples) | p50 | p95 | p99 | max |
|---|---|---|---|---|
| `/opc_hello` round-trip | 16.67 ms | 18.18 ms | 22.97 ms | 27.01 ms |
| 10 kB reply round-trip  | 16.67 ms | 17.31 ms | 19.49 ms | 20.95 ms |

The server collects RCON commands and runs them at the next tick. Pipelined
requests all land in the same tick: 300 pipelined `/opc_hello` calls took
85 ms (about 3,500 per second).

**Design impact:** sending one command and waiting for its reply caps out
near 30 Hz. At `poll_hz = 30`, 13 of 150 polls ran late; at 60 Hz, 292 of
300 did. **`poll_hz` will be limited to 1–30, default 10.** A poll cycle
should send its reads and writes together (pipelined) so they share one tick.

### 2. Each reply is a single packet, of any size
Replies of 100 kB, 1 MB and 10 MB each came back as one RCON packet, in about
22 ms, 80 ms and 500 ms. Factorio does **not** echo the empty "sentinel"
packet that many Source-RCON clients use to find the end of a multi-packet
reply. The client therefore reads exactly one packet per request and matches
it by request id. The original "reply size limit" risk doesn't apply. Large
replies cost time, though, so sending only changes still matters.

`rcon.print` adds a trailing `\n` to each reply.

### 3. RCON polling doesn't affect UPS
With auto-pause off, the game held **60.0 UPS** while polling at 10, 30 and
60 Hz with 10 kB replies, and at 10 Hz with 1 MB replies. The replies here
were generated by `string.rep`, so this doesn't yet measure the cost of
reading real circuit networks. That's still to be measured in milestone 5.

### 4. Auto-pause: each RCON command advances the game one tick
With the default `auto_pause: true` and no players connected, the game is
paused, but **each incoming RCON command advances it by one tick**.
Polling at 10 Hz made the game run at 10 UPS; with no polling it stayed
still (1 tick in 2 s).

**Design impact:** while auto-paused, the bridge itself slowly moves the
factory forward. Servers used with OPC should set **`auto_pause: false`**.
The bridge should show `tick_paused` and game speed under `Status/`, and
treat a tick that isn't advancing as "paused" rather than as a fault.

### 5. An uncaught Lua error in a command stops the server
`/opc_spike_error` raised a Lua error with nothing catching it. The server
moved to `Failed`, logged `Quitting: multiplayer error.`, and exited with
code 255.

**Design impact:** every handler now runs inside `pcall` (the `rcon_only`
wrapper in `control.lua`) and returns `{"ok":false,"error":"..."}`
instead. After that change, the same test returned the error as JSON and the
server kept running. **Every future command must go through this wrapper**,
and request parsing must assume input can be malformed.

### 6. Other observations
- Unknown commands return plain text (`Unknown command "..."`), not JSON.
  The bridge should treat a reply it can't parse as JSON as a protocol error.
- Mod commands work from RCON without `/c`, so achievements aren't affected.
  They're also blocked for players in game, because the wrapper rejects any
  call that has a `player_index`.
- The headless server can't reach `auth.factorio.com` from this sandbox, so
  `docker/server-settings.dev.json` uses LAN-only visibility and
  `require_user_verification: false`. Real deployments can use normal
  settings.

## Milestone 4: delta polling (`/opc_poll`)

Measured on 2026-10-17 on the dev server with 400 tags (200 writers, each
wired to a reader, 5 signals each), 20 samples:

| Request | Reply size | Round-trip |
|---|---|---|
| `/opc_snapshot` (all values) | 50,454 bytes | 37.5 ms |
| `/opc_poll`, full | 55,533 bytes | — |
| `/opc_poll`, nothing changed | 136 bytes | 16.8 ms (one tick) |
| `/opc_poll`, 10 writers changed | 1,105 bytes | — |

At this size a full read takes longer than one tick to build and encode,
and a quiet delta does not. Deltas still read every network in Lua; the
saving is in diffing instead of encoding and sending. The UPS impact of
reading many networks is still measured in milestone 5.

## Milestone 5: load test (`spike/load_test.py`)

Measured on 2026-10-17 on the dev server (4 cores, shared by the game, the
bridge and its OPC stack), with 5 signals per writer and the bridge at
10 Hz. Two layouts:
- **pairs:** each writer wired to its own reader, so N separate networks.
- **shared:** one writer and N readers on one network.

**Mod cost per poll**, timed with Factorio's own profiler. A full read
happens on every poll:

| Layout | Readers | Before M5 | After M5 | Share of 60 UPS budget at 10 Hz |
|---|---|---|---|---|
| pairs | 100 | — | 1.9 ms | 1.9% |
| pairs | 500 | 18.3 ms | 10.7 ms | 10.7% |
| shared | 100 | 1.3 ms | 0.7 ms | 0.7% |
| shared | 500 | 8.7 ms | 3.3 ms | 3.3% |

**Optimizations** made in M5:
- the sorted tag list is cached until tags change;
- writer outputs are cached in `storage` and audited round-robin (1/20 of
  the writers per poll);
- each circuit network is read once per poll however many readers share it;
- signal key strings are memoized.

Writers went from 6.8 ms to 0.25 ms for 500.

**What's left:** reading a network costs about 7 µs per reader in engine
calls. `get_circuit_network` and `get_signals` measured the same. So 500
separately wired readers still take about 10 ms. That cost lands on every
6th tick at 10 Hz, which can cause a visible hitch on a busy server.

**Advice:**
- Keep `poll_hz` low for large setups.
- Group readers on shared networks where possible.
- The option left if needed is spreading reads over several ticks.

**Max-UPS test.** The game ran at `game.speed = 1000`, and ticks per second
were compared with and without the bridge. The figures also include the
bridge's own CPU use on the same 4 cores, so they're an upper bound:

| Layout | Readers | Max UPS idle | Max UPS with bridge | Cost |
|---|---|---|---|---|
| pairs | 100 | 3141 | 3029 | 3.6% |
| pairs | 500 | 2718 | 2160 | 20.5% |
| shared | 100 | 3089 | 3021 | 2.2% |
| shared | 500 | 3198 | 2933 | 8.3% |
